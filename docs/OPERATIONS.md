# Эксплуатация и перенос данных

## SQLite: резервная копия и восстановление

1. Остановите сервер, чтобы аккаунты и рабочие пространства соответствовали одной точке времени.
2. Сохраните исходный `SUPPLY_MATCH_ENCRYPTION_KEY` отдельно. В локальном режиме ключ — `data/encryption.key`; архив его не содержит.
3. Выполните `python scripts/backup.py create backups/YYYY-MM-DD.smb`.
4. Выполните `python scripts/backup.py verify backups/YYYY-MM-DD.smb`.
5. Пробное восстановление: `python scripts/backup.py restore backups/YYYY-MM-DD.smb --destination restored-data`.

Архив защищён AES-GCM; каждая база дополнительно проходит расшифровку и SQLite integrity_check. Изменённый архив, неверный ключ и существующая папка назначения отклоняются. После восстановления аккаунтов все сессии, OAuth-состояния и одноразовые коды отзываются. Исходные базы не перезаписываются. Чтобы использовать результат, остановите сервер и перенесите восстановленные файлы в папку data, сохранив тот же ключ. Сначала проверьте на копии. Резервировать веса модели не требуется — их можно загрузить заново.

Периодичность резервирования и внешнее хранение настраивает оператор. Для автоматического ежедневного резервирования требуется окно остановки приложения; копирование на работающем сервере не даёт согласованной копии нескольких SQLite-файлов.

## PostgreSQL

Новый серверный backend работает с отдельной SQL-схемой для аккаунтов, системы и каждого личного пространства. Транзакционная блокировка схемы сохраняет последовательность изменений одного пространства между процессами. Пространства разных пользователей могут обслуживаться независимо. Поддержка многопроцессного хранилища не означает готовность всех остальных компонентов к горизонтальному масштабированию: локальный llama.cpp и фоновые задачи требуют отдельного планирования.

```sh
pip install -r requirements-server.txt
# Задайте URL через менеджер секретов, не записывая пароль в историю команд.
# SUPPLY_MATCH_DATABASE_URL=postgresql://.../supplymatch?sslmode=verify-full
python scripts/migrate_postgres.py           # проверка каждой схемы, с откатом
python scripts/migrate_postgres.py --commit  # перенос
python main.py --no-browser --no-ai-download
```

До переноса остановите приложение, сделайте и проверьте SQLite-копию. На целевой БД нужны права создания схем. Используйте отдельную БД и роль только для приложения. Для удалённого соединения нужны TLS с проверкой сертификата (`sslmode=verify-full`) и доверенный CA. Задавайте одинаковые URL, `SUPPLY_MATCH_ENCRYPTION_KEY` и при использовании `SUPPLY_MATCH_DATABASE_NAMESPACE` одинаковое пространство всем репликам. Пространство — до 16 символов `[a-z][a-z0-9_]*`; обычно оставляйте пустым.

Перенос сохраняет все таблицы и индексы, проверяет количество строк, восстанавливает последовательности числовых id. Непустая целевая схема отклоняется. Каждый файл переносится одной транзакцией; разные файлы — отдельными транзакциями. При остановке посередине уже перенесённые схемы сохраняются: не запускайте приложение до переноса всех файлов; для повторного полного переноса используйте чистую целевую БД. Исходные файлы не удаляются и не изменяются. Уберите URL для отката на исходную SQLite-копию, только если после миграции ещё не записывались новые данные в PostgreSQL.

В PostgreSQL записи не оборачиваются в прежние AES-GCM-файлы. Шифрование диска, доступ к БД, резервные копии и KMS настраиваются на сервере отдельно. Исходный ключ остаётся нужен для HMAC и связанных функций аккаунтов. CLI `scripts/backup.py` отказывает при активном PostgreSQL, чтобы не создать ложную копию старых SQLite-файлов. Используйте `pg_dump -Fc` и `pg_restore` в новую БД, отдельное шифрованное хранилище и периодическую проверку восстановления. Документация транзакций: [Psycopg](https://www.psycopg.org/psycopg3/docs/basic/transactions.html).

## Проверка PostgreSQL

```sh
# Только отдельная тестовая БД, не production.
SUPPLY_MATCH_DATABASE_URL=postgresql://localhost/supplymatch_test python scripts/test_postgres.py
```

Проверки создают случайные схемы `test_*` и удаляют только созданные своим запуском схемы. Проверяются импорт/сравнение/корзина, изоляция, CSRF, восстановление доступа, конкурентный лимит и перенос SQLite. Производительность под целевой нагрузкой и резервное восстановление production требуют отдельных замеров.

## Мобильная проверка

```sh
npm install --ignore-scripts --package-lock=false
node scripts/prepare-mobile.mjs
cd mobile
../node_modules/.bin/cap sync
cd android
./gradlew assembleDebug
```

Нужны Node 22+, Java 21, Android SDK; для iOS — полноценный Xcode. URL API задаётся через `SUPPLY_MATCH_MOBILE_API_URL` до подготовки ресурсов; секреты не входят в клиент.

GitHub Actions собирает Android debug APK как артефакт `supply-match-android-debug`. Это тестовая сборка, не публикация в магазине. Подпись release, Apple provisioning и тестирование на реальных устройствах требуют настроек владельца. Проверьте вход, сохранение сессии после перезапуска, выход на всех устройствах, возврат из оплаты, импорт с устройства, небольшие экраны и отсутствие сети.
