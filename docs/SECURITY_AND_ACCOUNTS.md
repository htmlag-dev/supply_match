# Аккаунты и размещение на сервере

Реализованы регистрация по email/паролю, вход, выход, роли user/admin, блокировка аккаунта с отзывом всех сессий, личные базы и админ-панель пользователей, заявок, покупок, платежей и журнала входов. На старте приложения нужна авторизация. Существовавшая общая база перенесена в личный аккаунт локального администратора. Новые пользователи начинают с пустой базы.

Единственный администратор текущей установки: логин `alexapp`. Пароль задан владельцем, хранится только хешем внутри зашифрованной базы и не записан в файлы проекта. Остальные аккаунты имеют роль user. Сменить пароль: `python scripts/admin.py reset-password --email admin@supplymatch.local`. Создать другого администратора: `python scripts/admin.py create --email your@email.example` — пароль вводится скрыто, общих стандартных паролей нет. Первый зарегистрировавшийся пользователь не получает роль администратора.

Пароли: scrypt N=131072/r=8/p=1, индивидуальная случайная соль; одновременно не более двух операций хеширования. Сессии: случайные 256-битные токены, в базе только SHA-256, срок 30 дней без автоматического выхода из-за простоя. Для браузера — HttpOnly cookie, SameSite=Lax, Secure при HTTPS. Мутации требуют отдельный CSRF-токен. IP и User-Agent сохраняются как HMAC-SHA256, а не открытые значения; смена IP не отзывает сессию. Для reverse proxy включите SUPPLY_MATCH_TRUST_PROXY=1 и перезаписывайте X-Real-IP реальным адресом клиента (не доверяйте входящему пользовательскому заголовку). Есть выход на одном или всех устройствах. На мобильном клиенте сессия передаётся заголовком Session и привязана к адресу выбранного сервера. Токен сохраняется через @aparajita/capacitor-secure-storage в iOS Keychain / Android Keystore, без синхронизации iCloud, с доступом только на этом устройстве. Пароли не запоминаются. Нативное хранение нужно проверить на настоящих устройствах после сборки; APK/IPA здесь не собраны. Есть ограничения частоты входа/регистрации и серверная проверка ролей. Роль нельзя назначить при регистрации.

`data/accounts.enc`, `data/system.enc` и `data/workspaces/*.enc` шифруются AES-256-GCM со случайным nonce при каждом сохранении, с проверкой целостности. SQLite работает в оперативной памяти, на диск атомарно записывается зашифрованный снимок; незашифрованных journal/WAL для этих хранилищ нет. Старая локальная база после проверки переноса сохранена как `data/legacy-backup.enc`. Данные доступны приложению в памяти во время работы. Это не сквозное шифрование: сервер и администратор с ключом могут читать данные.

В локальной версии ключ автоматически создаётся в `data/encryption.key`. Копирование всей папки вместе с ключом позволяет расшифровать данные — не храните ключ рядом с базами в production. На сервере задайте **тот же** ключ через `SUPPLY_MATCH_ENCRYPTION_KEY` из секрет-хранилища (base64url от 32 байтов). Не генерируйте новый ключ для уже существующих данных: доступ будет потерян. Ключ и резервные копии храните отдельно. Для новых серверных данных создайте новый криптографически случайный ключ. Не размещайте папку data, .env и исходники как публичную папку веб-сервера. Сервер раздаёт только явно перечисленные файлы интерфейса.

Установка: `python -m pip install -r requirements.txt`. `.env.example` — образец, приложение **не загружает .env автоматически**: задайте переменные окружения процесса через менеджер службы/секретов. Для production нужны `SUPPLY_MATCH_ENV=production`, `SUPPLY_MATCH_PUBLIC_URL=https://your-domain.example`, `SUPPLY_MATCH_PUBLIC_HOST=your-domain.example`, ключ шифрования. Запуск `python main.py --no-browser` только на 127.0.0.1 за HTTPS reverse proxy. `--lan` в production запрещён. Ограничьте тело запроса до 200 KB, число одновременных соединений и частоту запросов на reverse proxy, разрешите входящие только 443. Прокси должен сохранять Host. Указывайте разрешённые мобильные origins в `SUPPLY_MATCH_ALLOWED_ORIGINS`; не используйте `*`.

Хранилище рассчитано на **один серверный процесс**, с блокировкой операций по файлу. Не запускайте несколько workers/реплик на общей папке. Для значительного числа пользователей потребуется серверная СУБД и KMS; текущая реализация заново шифрует снимок базы при изменении. Админ-список ограничен 500 аккаунтами. Ротация ключа без миграции не поддерживается. Восстановление пароля доступно по email: одноразовый код на 10 минут, не более пяти попыток, ограничение частоты и отзыв всех сессий после смены. Владелец также может сбросить пароль через консоль. MFA пока не добавлена; подтверждение email реализовано одноразовым кодом (см. ниже). Перед открытым коммерческим запуском нужны независимая проверка безопасности, мониторинг, проверка резервного восстановления и настройка этих процессов. Невзламываемых приложений не существует.

## Google

Создайте OAuth client типа Web application. Укажите redirect URI `https://your-domain.example/auth/google/callback`, задайте GOOGLE_CLIENT_ID и GOOGLE_CLIENT_SECRET на сервере. Используются authorization code + PKCE, state, nonce; сервер проверяет подпись ID token по JWKS, issuer, audience, exp, iat и nonce. [Документация Google](https://developers.google.com/identity/openid-connect/openid-connect).

## Apple

Нужны Apple Developer, Services ID с доменом/return URL `https://your-domain.example/auth/apple/callback`, Sign in with Apple key (.p8), Team ID и Key ID. APPLE_CLIENT_ID — Services ID; APPLE_CLIENT_SECRET — подписанный ES256 JWT, а не текст .p8. Вспомогательный скрипт `python scripts/apple_client_secret.py` создаёт JWT на 30 дней в приватном файле data/apple-client-secret.txt; перенесите значение в секрет-хранилище и обновляйте до истечения. Сервер принимает Apple form_post callback, одноразово проверяет state с привязкой к браузеру, обменивает code и проверяет подписанный ID token. [Документация Apple](https://developer.apple.com/documentation/signinwithapple/authenticating-users-with-sign-in-with-apple).

При отсутствии реквизитов кнопки Google/Apple отключены. Без реальных credentials и публичного HTTPS-домена полный вход провайдеров не проверен; это серверная интеграция, а не имитация успешного входа. Автоматическое объединение аккаунтов по совпадающему email отключено. В нативных сборках сейчас используется email/пароль; OAuth через системный браузер с возвратом в нативное приложение требует отдельной настройки Universal/App Links и пока доступен через веб-версию.

## Платежи

Общий webhook ЮKassa: `https://your-domain.example/api/payments/webhook`. Связь payment_id → пользователь хранится на сервере, не принимается из произвольного клиентского user_id. Webhook не доверяет присланному статусу: получает платёж из API магазина и сверяет реквизиты заказа. Админ-панель показывает результаты и не позволяет вручную пометить заявку оплаченной. Для аварийного восстановления индекса: для каждого пользователя вызвать `AuthService.index_payments(user_id, workspace)` из серверной консоли. Пока платёжные секреты не заданы, сохраняются заявки без списания.

## Подтверждение почты

Новые регистрации проходят проверку шестизначным кодом из письма. Код действует 10 минут, одноразовый, не более пяти попыток; повторная отправка через 60 секунд, до пяти отправок в час на аккаунт и дополнительные ограничения по IP. В базе — только HMAC кода и хеш идентификатора проверки. Не подтверждённый аккаунт не получает сессию и доступ к API, покупкам или личной базе. Успешная проверка открывает обычную 30-дневную сессию. Вход через Google/Apple доверяет только проверенному подписанному email_verified провайдера. Аккаунт владельца alexapp сохранён как доверенный администратор.

Для реальной отправки задайте SUPPLY_MATCH_SMTP_HOST, SMTP_PORT, SMTP_SECURITY (ssl для 465 или starttls для 587), SMTP_FROM, SMTP_USER и SMTP_PASSWORD в окружении сервера. Пароль почты не вводите в интерфейс клиента и не публикуйте в репозитории. Используется TLS с проверкой сертификата; коды не выводятся в логи, API и локальные почтовые файлы. Если SMTP не настроен или не принял письмо, регистрация сообщает об ошибке, а не имитирует отправку. В текущем окружении SMTP-реквизитов нет, реальная доставка в почтовый ящик не проверялась. Протокол подтверждения проверен автоматическими тестами и в браузере с изолированным тестовым почтовым адаптером.

Операции администрирования через scripts/admin.py выполняйте при остановленном сервере: файловое хранилище рассчитано на один процесс. Пароль владельца задан по его инструкции; перед публичным размещением замените короткий пароль длинным уникальным. Абсолютная защита от взлома не гарантируется.
