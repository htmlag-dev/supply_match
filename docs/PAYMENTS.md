# Подключение платежей

В приложении два независимых вида заказа:

1. `subscription` — подписка Профи на Supply Match.
2. `purchase` — оплата физического товара конкретному продавцу.

Суммы определяет сервер. Для подписки используется каталог тарифов, для товара — согласованные пользователем количество, цена и доставка. У товара нет автоматического подтверждения цены продавцом: её нужно согласовать до оплаты.

## Без платёжных реквизитов

Страницы уже работают: тариф или товар оформляется в заказ, сохраняется сумма, контакт и идентификатор. Статус — `awaiting_integration`. Деньги не списываются; платная подписка не включается. Нет сбора карточных данных и фиктивного «успешного платежа».

Оформление товара само по себе не отправляет заказ или адрес продавцу и не резервирует остаток. После оплаты нет автоматической логистики, escrow или защиты сделки.

## ЮKassa

Адаптер реализован в `app/services/payment_service.py`. Для подписки задайте переменные **в среде серверного процесса**:

```text
SUPPLY_MATCH_BILLING_SHOP_ID=<идентификатор магазина приложения>
SUPPLY_MATCH_BILLING_SECRET=<секретный ключ этого магазина>
SUPPLY_MATCH_PAYMENT_RETURN_URL=https://ваш-домен/#pricing
```

Для оплаты товаров продавцу с ID `7`:

```text
SUPPLY_MATCH_SELLER_7_SHOP_ID=<идентификатор магазина продавца>
SUPPLY_MATCH_SELLER_7_SECRET=<его секретный ключ>
```

Учётные данные продавца настраиваются владельцем сервера, а не покупателем в браузере. Реквизиты никогда не возвращаются клиенту. Поддержанный адаптер принимает RUB; заказы в других валютах сохраняются без попытки списания. Для международных и частных продавцов нужны подходящие платёжные подключения и онбординг — произвольный контакт из AI-поиска автоматически получателем денег не становится.

Настройте уведомления ЮKassa на:

```text
https://ваш-домен/api/payments/webhook
```

Endpoint уведомлений не требует токена пространства: подлинность результата проверяется **повторным запросом `GET /v3/payments/{id}` к ЮKassa с секретом магазина**. Сверяются ID, получатель, сумма, валюта и metadata заказа. Присланным клиентом полям `paid`/`amount`/`status` приложение не доверяет.

Сценарий:

1. `POST /api/billing/checkout` или `POST /api/purchases` сохраняет заказ.
2. При настроенных реквизитах сервер вызывает `POST /v3/payments` с `Idempotence-Key`, равным ID заказа.
3. Клиент получает HTTPS-ссылку и открывает защищённую страницу провайдера. В мобильном клиенте товары открываются через native Browser plugin.
4. Сервер получает уведомление и запрашивает платёж у провайдера.
5. Подтверждённая оплата товара помечает заказ как `paid`. Оплата подписки активирует Профи на календарный месяц или год. Повторное уведомление срок не продлевает.
6. Пользователь возвращается и обновляет статусы; редирект не меняет статус сам по себе.

Повторное оформление с тем же ключом и данными возвращает тот же заказ/платёж. Другие данные с тем же ключом отклоняются. Чужую сумму из браузера подписка игнорирует.

**Перед реальным запуском:** проверьте тестовый магазин, настройки чеков/фискализации для вашего платёжного аккаунта, сценарии отмены и возврата, личный кабинет продавца и рабочий публичный HTTPS endpoint. В текущем адаптере нет отправки чеков и API возврата. Боевые реквизиты не были предоставлены, реальные списания не выполнялись. Настройка окружения сама по себе не заменяет проверку платёжного аккаунта.

Подписка на цифровые возможности мобильного приложения требует отдельного store billing-подключения для выпуска в магазинах. В native-клиенте сейчас сохраняется заявка; платежи за физические товары отделены от подписки.

Официальный API: https://yookassa.ru/developers/api
